## 2. Що вже є (Факт на 25.10.2026) і чого немає

**Є в базі й коді (`archi_recalc_stages`, live):**
- `project_metrics.bac` = бюджет собівартості з Кошторису (K6sm: `E7`; = команда `G7` + субпідряд `H7`);
- AC = `actual_cost` (години × ставка + оплачені субпідрядники, `статус='confirmed'`);
- `pct_complete` (готовність ПМа, зважена по плану годин стадій; лише коли дано всі 4 стадії);
- `ev_classic_evm = bac × pct_complete`, `cpi_classic_evm = ev_classic_evm / actual_cost` (DEMO-03 = 0,9065);
- `payment_schedule` (акти й дедлайни документації по стадіях — події, не часовий розклад вартості).

**Немає:** PV (план вартості в часі), SPI, SV, CV як окремі поля, EAC/ETC/VAC/TCPI у класичному вигляді, екрана «EVM (класичний)», EVM-блоку в Кошторисі, бота, що пропонує його наповнити.

**Структура Кошторису, яку читає K6sm (Факт, код `Parse And Validate`, воркфлоу `K6smBd5xWZLWx9rr`):**
- Вкладка проєкту, діапазон `A1:X27`: `A1` = ID проєкту; `A3` = рентабельність; `A5` = ставка; `D7/E7/F7/G7/H7` = контракт / собівартість (BAC) / прибуток / команда / субпідряд; `W1` = години всього; рядки стадій 13 (МБР), 17 (ЕП), 21 (П), 25 (Р), 27 (АН) із `B = TOTAL`, години в `D`.
- Вкладка `Графік_оплат`, діапазон `A1:N2000`: колонки `ProjectID`, `Стадія`, `Дата_план`, `Сума_план`, `Ймовірність_10`, `Статус`, `Дедлайн_документації_план`, `Ймовірність_видачі_10`.
- Перевірки K1–K11 (K1–K8, K9 блокують; K10, K11 — попередження).
- **Не перевірено:** решта комірок вкладки поза цими; Google Sheets MCP у сесії потребував повторного входу (26.10.2026). **Перший крок EVM-сесії — прочитати реальну вкладку проєкту** (через Sheets MCP після входу або n8n-допоміжний воркфлоу `nGcSyWfuMO7vjTn6` «Archi: Sheets Helper»).

## 4. Архітектура (від кінця до початку; інваріант єдиного обчислення — `TECH_SPEC` §2.1)

```
Кошторис (вкладка проєкту + нова вкладка «EVM_план»)  ←── Sheets Helper (n8n)  ←── бот: «📈 Додати дані для EVM?» (генерація за запитом)
        │ K6sm (preview/commit; нові перевірки E1…E5; опційно)
        ▼
 project_metrics.bac …  +  evm_baseline (project_id, період, pv_cum)      ← опційно
        │                         │
        ▼                         ▼
 archi_recalc_stages (AC, EV)  →  SQL-в'ю evm_classic_today (+ функція на дату знімка для історії)
                                   BAC, PV, EV, AC, CV, SV, CPI, SPI, EAC, ETC, VAC, TCPI, «станом на»
        ▼
 Build MiniApp Data (лише відображення) → Build MiniApp HTML: вкладка «EVM (класичний)» (код вузла, **без** патч-вузлів)
```

- **Обчислення — тільки в SQL** (в'ю), JS лише форматує. Нових порогів Archi не використовує.
- **Опційність графіка:** якщо `evm_baseline` для проєкту порожня → PV, SV, SPI = «немає базового плану»; CPI, CV, EAC, ETC, VAC, TCPI рахуються з BAC, EV, AC.
- **Готовність (EV) — оцінка ПМа** (відома межа, M9); вкладка підписує джерело.
- **Бот:** у `WR: Hard Logic Engine` нові режими (напр. `evm_offer`, `evm_generate`, `evm_confirm`); маршрут у `WR: Route`; пропозиція — inline-кнопки; запис у Кошторис через `Archi: Sheets Helper` (`nGcSyWfuMO7vjTn6`); `K6sm` розширюється читанням вкладки `EVM_план` (опційно) і новими перевірками (див. нижче).
- **Перевірки EVM-блоку в K6sm (пропозиція, `warn`, не блокують існуючий план):** E1 — сума PV на кінець = BAC (± 1 грн); E2 — PV накопичувально не спадає; E3 — періоди послідовні, перший ≥ початок договору; E4 — по стадіях сума PV стадії = собівартість стадії; E5 — кожна стадія з планом > 0 має рядок.

## 7. Ризики

- **Змішування методологій:** вкладка не може брати пороги/назви Archi; у підписах — «класичний EVM».
- **Суб'єктивний EV (готовність ПМа):** CPI/EAC так само чутливі, як і Archi; підпис «оцінка ПМа».
- **Опційний PV:** користувач може сприйняти «немає базового плану» як помилку — текст має пояснювати.
- **Генерований графік — модель:** рівномірний розподіл між датами стадій не є планом ПМа; бот має це казати, а власник — редагувати перед «затвердити».
- **Запис у Кошторис:** Google Sheets MCP бува недоступний; запис лише через n8n (`nGcSyWfuMO7vjTn6`), preview завжди перед записом.
- **Крихкість n8n:** нові вузли поруч із `Doc Intake` та `K:` — не змінювати Y-координати наявних сестринських гілок (CTO #5).
- **Обсяг:** це 4–5 сесій; не змішувати з параметризацією SQL.
