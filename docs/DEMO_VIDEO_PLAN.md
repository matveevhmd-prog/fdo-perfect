## 3. Фіча 3 — що саме "не пропрацьовано" (аудит)

Факти з репо (не з пам'яті):

1. **Шаблон звіту існує тільки як JSON-схема всередині промпту**
   `WR: Build WR Prompt` (5 секцій). Як окремий, показуваний клієнту артефакт
   ("ось шаблон, який отримує ваш ПМ") — **не існує.**
2. **"Бріф ПМ" — не існує.** Слово "брифінг" у репо означає інше: обов'язковий
   розбір плану минулого тижня всередині WR-діалогу. Документа/екрана "що ПМ
   має підготувати до п'ятниці, як заповнювати, приклад" — немає.
3. **Щотижнева таблиця для наради** — є Weekly Render (`Weekly Render Page
   Webhook`), але: (а) не перевірено, що він показує ВСІ проєкти однією таблицею
   на великий екран (Образ §4.1: вівторок 9:30, показ екрану) — а не по одному;
   (б) Образ забороняє грошові суми в рендері, Owner View їх показує —
   це різні аудиторії, але у відео треба явно розвести; (в) після Package 1
   (25–26.09) Weekly Render окремим прогоном не перевірявся — **Потребує перевірки.**
4. **Єдина система** (пункт 1+2+3 власника): зв'язка існує технічно
   (WR → `wr_weekly_snapshots` → `archi_recalc()` → `project_metrics` → усі
   екрани), але не **показана як цикл** П'ятниця→Вівторок. Це сценарний, а не
   інженерний борг.
5. Відкрите з Спеки: `meeting_log` — 3 backfill-рядки, жива інтеграція не
   вирішена → Q10 ("що пообіцяли на нараді") **чесно відповісти не може**.

## 4. План робіт (від кінця до початку)

### Фінал: відео, яке можна показати клієнту
Зворотний ланцюг: відео ← сценарій + чисті DEMO-дані ← 3 фічі працюють наживо ←
Weekly-артефакти (шаблон, бріф, таблиця) ← фіксація Q1–Q10 ← рішення власника.

### Етап 0 — Рішення власника (Розділ 5). Без них не стартувати Етап 2.
### Етап 1 — Фіксація фіч (документ, без змін у n8n) — ~0.5 дня
1.1 `docs/ARCHI_FEATURES_v1.md`: 3 фічі, що входить / не входить, для кожної —
    "що клієнт побачить у відео" (1 абзац) і критерій "готово".
1.2 Зафіксувати Q1–Q10 з джерелом даних кожного (таблиця 4.2).
### Етап 2 — Щотижневий ритм (Фіча 3) — ядро роботи
2.1 **Шаблон звіту** — винести з промпту в документ + рендер-приклад
    (5 секцій, без грошей). Один файл правди, на який посилається і промпт.
2.2 **Бріф ПМ** — 1 сторінка: що збирати до п'ятниці 17:30, 3 питання
    (скільки залишилось / що завадить / чим допомогти), приклад диктовки,
    як працюють команди бота (`проєкт X`, `чернетка`, `фінал`, `скасувати`).
    Може видаватись самим ботом командою (напр. `бріф`) — **рішення власника.**
2.3 **Щотижнева таблиця на великий екран** — перевірити живо Weekly Render:
    усі проєкти одним екраном, читабельність з 3 м, колонки-тижні, кольори.
    Якщо ні — доробка рендеру (окремий пункт, оцінка після перевірки).
2.4 **Наскрізна репетиція ритму на DEMO:** пт диктовка → фінал → вів. рендер.
    Перевірка SQL по `wr_weekly_snapshots`/`project_metrics`, не `status: success`.
### Етап 3 — Archi Consult (Фіча 2)
3.1 Кнопки/команди Q1–Q10 у чаті (і/або Owner View) — **варіант А (рек.)**:
    детерміновані відповіді з `project_metrics` + LLM лише форматує
    (Insight–Impact–Action). Не LLM-вигадка — відповідає Директиві Істини.
3.2 Для Q без даних — чесна відповідь "даних немає, потрібно X" (не обрізання
    питання з набору — набір LOCKED).
3.3 Довільні питання: набір з ~10 тестових запитів, перевірка формату IIA і
    відсутності вигаданих метрик (правила Спеки §7).
### Етап 4 — Owner View (Фіча 1)
4.1 Власник особисто проходить Owner Morning Test на `archi_recalc()`
    (закриває відкритий чекпоінт 4 і UX-огляд 9.4).
4.2 Виправлення знайдених розбіжностей.
### Етап 5 — Демо-середовище і відео
5.1 Чисті DEMO-дані: сценарій потребує 2–3 "історій" (проєкт у червоному,
    в жовтому, блокер ⛔, розбіжність ⚖️). Перевірити, що вони є; дописати SQL-
    сидом, якщо ні.
5.2 Безпека кадру: у відео не показувати URL n8n-інстансу в адресному рядку,
    токен/JSON workflow, Supabase. Бот `@archi_demo_bot` з'явиться — прийнятно.
5.3 Сценарій відео по кроках (раскадровка): Ритм (пт→вт) → Таблиця на екрані →
    Owner View → Consult Q1–Q10 → вільне питання. Порядок — **рішення власника**
    (рекомендація: починати з Ритму, бо це продає "систему", а не "дашборд").
5.4 Репетиція, запис, фіксація в `RELEASE_PLAN.md` (новий розділ).

### 4.2 Q1–Q10 — чи є дані в Data Total (Припущення, потребує перевірки живим SQL)

| Q | Питання | Джерело | Оцінка |
|---|---|---|---|
| 1 | Що відбувається | `project_metrics`, кольори | є |
| 2 | Де запалає | кольори, ⛔, ⚖️, CPI | є |
| 3 | Чи треба щось робити | похідне від 1–2 | є |
| 4 | Гроші на зарплату | потрібен кеш/зарплатний фонд | **немає в Data Total** |

| 8 | Дедлайни | `nearest_doc_deadline`, `payment_schedule` | є |

Висновок: щонайменше Q4, Q9, Q10 у поточній схемі без рішення відповісти не
можуть. Це прогалина продукту, а не відео — або розширюємо Data Total (рішення
власника, межа Data Total вже змінювалась), або у відео ці питання показують
як "Archi чесно каже, яких даних не вистачає".
