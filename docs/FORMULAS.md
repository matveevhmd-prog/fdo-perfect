## 0. EVM — методологічна база (рішення власника 21.10.2026, `CLAUDE.md` п.7)

Скрізь, де це можливо, показники тлумачаться як EVM-індекси. Одиниці — **години** (BAC = `planned_hours`, AC = Σ `time_log.години`, ETC = прогноз ПМа). Weekly Render не показує сум грошей: лише % і індекси «план = 1,00».

| ID | Показник | Формула | Читання | Приклад DEMO-01, 12.10 (live SQL 21.10.2026) |
|---|---|---|---|---|
| E-01 | Витрачено часу (PV за часом) | AC ÷ BAC | скільки планового часу витрачено; якщо все за планом, готовність мала б дорівнювати цьому | 56,1% |
| E-02 | Готовність ПМа (EV) | Σ (готовність стадії × плановий ETC стадії) ÷ Σ плановий ETC | оцінка ПМа, зважена по стадіях (= `earned_value_contract` ÷ контракт) | 55,7% |
| E-03 | Готовність за прогнозом | AC ÷ EAC, EAC = AC + ETC_прогноз | яка частка роботи реально зроблена, якщо вірити залишку ПМа | 55,6% |
| E-04 | Розбіжність готовності, п.п. | E-02 − E-03 | ПМ завищує готовність відносно власного залишку = технічний борг; Weekly Render/чат ПМа: E-02 − E-03 ≥ `wr_ready_gap_pp` (10 п.п.) → 🔴 (`archi_ready_gap_signal`; лише в бік завищення; від’ємна розбіжність 🟢 — власник 22.10.2026); Owner View S-12 лишається 20 п.п. 🟡 | +0,1 п.п. 🟢 |
| E-05 | Ефективність годин | BAC ÷ EAC (власник: «план / (факт + прогноз)»; було в рядку 3 як EAC ÷ BAC = 100,8% — зворотне) | 1,00 = за планом; < 1 перевитрата годин; колір (`archi_idx_signal`): 🔴 < `idx_red` 0,7; 🟡 < `idx_yellow` 0,9; > 1 (економія годин) 🟢 (власник 22.10.2026) | 0,99 |
| E-06 | Акти ÷ освоєний обсяг | Σ підписаних актів ÷ (контракт × готовність ПМа) | 1,00 = виставлено стільки, скільки освоєно; < 1 недофактуровано. Колір (`archi_flow_idx_signal`): < `idx_yellow` 0,9 → 🟡, < `idx_red` 0,7 → 🔴 | 0,40 🔴 |
| E-07 | Оплата ÷ Акти | Σ надходжень ÷ Σ підписаних актів | 1,00 = оплачено все підписане; > 1 аванс; < 1 заборгованість. Колір (`archi_paid_idx_signal` = `archi_flow_idx_signal`): < 0,9 🟡, < 0,7 🔴; > 1 (аванс) 🟢 — краще за план (власник 22.10.2026). У підписі «(>1 — аванс)» | 2,05 (аванс) 🟢 |

Принцип власника (22.10.2026): 🟢 = краще за план або за планом, 🟡/🔴 = гірше за план; «плюс» ніколи не жовтий/червоний. Пороги E-06/E-07: жовтий нижче 0,9, червоний нижче 0,7; E-04: ≥ 10 п.п. завищення → 🔴; H-02 (ETC Δ): Δ ≤ 0 → 🟢, Δ > 0 — 5%/10% від ETC_факт.

## 7. Відомі проблеми визначень (потрібні рішення власника)

1. ~~Дві бази рентабельності~~ — **закрито 16.10.2026 (власник):** показувати обидві проєкції. Картка проєкту: «Рентабельність від контракту» і «від собівартості» (План \| Факт \| Прогноз; колір S-02 лише за базою «від контракту»); портфель: P-07 і P-04 окремими рядками. Факт від контракту = прибуток факт ÷ підписані акти, від собівартості = ÷ Собівартість_факт.

   резервними значеннями `|| 0.10 / 0.05 / 0.4 / 50`. Значення збігаються з БД, але це
   друге місце обчислення; плюс `||` підмінить законний 0 у БД. Перенести в
   `Build MiniApp Data`.
3. ~~ETC: повний план стадії проти залишку~~ — **закрито 16.10.2026:** стадійний блок і S-04 порівнюють F-04 з плановим залишком (F-23); у S-05 лишився повний план D-03 (свідомо).
4. ~~ETC_Total у картці~~ — **закрито 16.10.2026:** План / Факт / Прогноз = F-23 / F-23 / F-06, усі без АН.

   не погоджена (альтернатива — проти актів).
7. **Свіжість прогнозу не контролюється:** останній звіт ПМа по DEMO-проєктах —
   21.09.2026 (24 дні на 15.10.2026), сигналу «прогноз застарів» немає (див. TECH_SPEC v3 §8).

   `статус='confirmed'`, на відміну від F-17/F-18.

   Q7 цитує `pfc` (Прибуток, Рентабельність бізнесу, Проєкти — план/факт/прогноз) і
