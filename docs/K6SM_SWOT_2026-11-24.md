## 3. Ідеї за напрямами

Позначка **[док]** — ідея спирається на документ; **[нова]** — немає в документації, потребує вашого рішення.

### 3.1 Стабільність
1. **Відбиток файлу [док: п. 41, M1б]**: при перегляді рахувати контрольну суму прочитаних значень і зберігати з чернеткою версії. «Затвердити» застосовує саме цю чернетку, а не перечитує файл. Файл не міг змінитись між кроками.
2. **Різні діагнози помилок [нова]**: «немає доступу», «немає вкладки», «ліміт API», «структура порушена» — окремі повідомлення з дією.
3. **Повтор при тимчасовій помилці [нова]**: 2 спроби з паузою на 429 і 5xx. Розрахунок виконань: до 2 додаткових викликів на помилку, не на кожен запуск.
4. **Читання за маркерами, а не за номерами рядків [нова]**: знаходити блоки стадій за значенням `TOTAL` у колонці B. Додатковий рядок у розділі більше не ламає імпорт.
5. **Ідемпотентність [док: §213]**: повторне затвердження тієї ж чернетки нічого не змінює (вже є в SQL).

### 3.2 Оптимізація
1. **Перенести всі перевірки й розрахунки в SQL [док: п. 31]**: вузол читає файл у JSON і викликає `koshtorys_preview`. Code-вузол зменшується до розбору комірок.
2. **Один запуск замість двох [нова]**: чернетка версії зберігається в базі, «затвердити» викликає `koshtorys_approve` без повторного читання Google. Мінус: один виклик Google і один запуск n8n на проєкт (п. 43, правило 14).
3. **Не стирати графік оплат, а версіонувати [док: D-1, п. 40]**: графік входить у версію Кошториса.
4. **Прибрати зашитий ID файлу й тестовий режим із бойового вузла [нова]**.

### 3.3 Релевантність повідомлень
1. **Що зміниться [док: `koshtorys_diff`]**: порівняння з чинною затвердженою версією: контракт, години по стадіях, вартість, рентабельність у п.п. Власник бачить різницю, а не весь план.
2. **Кожна ❌ з конкретикою [нова]**: комірка файлу, очікуване й фактичне число, що виправити. Приклад: «E7 = 548 500, а G7 + H7 = 548 547,86: різниця 47,86 грн».
3. **Ролі [док: п. 39]**: прев'ю з грошима лише власнику й ПМу; виконавцю — без грошей.
4. **Попередження без жовтого для відхилень від плану [док: п. 15]**: ⚠️ лишається лише для якості даних (K10, K11), а не для відхилень.
5. **Короткий текст [нова]**: показувати блоки актів і документації стисло, якщо вони не змінились.
6. **Дія готовим текстом [док: п. 32]**: «Що зробити» у форматі «Insight → Impact → Action».

### 3.4 Самонавчання
1. **Журнал результатів перевірок [нова]**: який код перевірки, проєкт, ПМ, час, пройшла чи ні. З нього видно, які помилки повторюються й у кого.
2. **Профіль колонок клієнта [док: п. 22]**: після першого успішного імпорту запам'ятовується відповідність колонок цього клієнта.
3. **Історичний коефіцієнт [док: п. 37, W2.15]**: план годин по стадіях проти фактичного співвідношення по завершених проєктах цього бюро. Формула в SQL, поріг — параметр `archi_thresholds`; назву й значення порога визначаєте ви.
4. **Нові розділи й виконавці [нова]**: якщо розділу немає в довіднику, пропонувати додати його (власник підтверджує), а не лише відмовляти.
5. **Причини відхилень [док: п. 41 «Санкція»]**: «скасувати» — з короткою причиною; повторювані причини стають підказками. Між клієнтами лише знеособлений шар (п. 28).

### 3.5 Результативність
1. **Шлях «файл → затверджений план» в один діалог [док: п. 41]**: бот приймає файл, показує різницю, одне «затвердити», версія й посилання на файл зберігаються.
2. **Додаткова угода при зміні після затвердження [док: п. 41]**: якщо план змінюється, бот пропонує оформити угоду; «Хто платить за зміну» виводиться зі статусу угоди.
3. **Звірка з договором [док: п. 41]**: сума контракту у файлі проти документа проєкту (скан договору).
4. **Метрики вузла [нова]**: частка імпортів, що пройшли з першого разу; час від файлу до затвердження; кількість повторів. Лише вимірювання, без оцінок.
