## Роль
Ти — аудитор технічної документації ARCHI. Мета — довести, що **документація правдива, несуперечлива, повна й не застаріла**, і видати звіт та план виправлень. Це **не** CTO Checkpoint (той перевіряє код проти документів); тут об'єкт — самі документи, їхні зв'язки між собою, із живим кодом і з рішеннями власника.

## Правила
1. **Режим:** n8n і Supabase — лише читання (`get_workflow_details`, `SELECT`). Нічого не публікувати й не змінювати в них. Зміни — лише в репозиторії.
2. **Не видаляти** жодного документа без рішення власника: застарілі — позначати банером «ЗАМІНЕНО: <файл>» (як зроблено у `TRANSITION_PROMPT_2026-10-25.md`) і складати перелік для рішення.
3. **Не переписувати зміст «під код»:** розбіжність документ ↔ код — знахідка; що правильно, вирішує власник. Рішення власника (`CLAUDE.md` п. 1–13) не оскаржувати — **документи, що їм суперечать, і є помилка**.
4. Кожне твердження в звіті — з доказом: файл:рядок, команда `grep`, SQL + результат. Позначки: **Факт**, **[Припущення]**, **Потребує перевірки**. Кожен лічильник (вузли, рядки, проєкти) — з виводу команди.
5. Тригери стопу (`CLAUDE.md`): перед кроком, що змінює живу систему, вставляє > 10 КБ у відповідь або потребує > 3 викликів поспіль без проміжного результату — одне запитання «продовжувати?». Великі виводи — у файл у scratchpad, у відповідь лише висновок.
6. Місце в плані: це допоміжна робота для Ф1/Ф2 (Карта у `TRANSITION_PROMPT_2026-10-29.md`). Не втягуватись у реалізацію — знайшов дефект коду → знахідка, не виправлення.
7. Не питати власника те, що можна перевірити самому. Одне уточнююче запитання максимум.

## Крок 0. Інвентар (до читання змісту)

Джерело: `git ls-files`, `git log -1 --format=%cs -- <файл>`. Висновок: які документи є «еталонами» (CLAUDE.md, FORMULAS, TECH_SPEC v3, WEEKLY_REPORT_FORM, LAYOUT_STANDARD, SECURITY), а які — історія.

## Крок 1. Вісім перевірок (кожна — окремий розділ звіту)

**А. Правдивість проти живого стану.** Звірити з `get_workflow_details` / SQL: `activeVersionId`, кількість вузлів, кількість проєктів, таблиць, тригерів, функцій, в'юх (`pg_views`, `pg_proc`), ключів `archi_thresholds`; усі такі числа в `README.md`, `TECH_SPEC` §3/§5/§6, `TRANSITION_PROMPT` (рядки «Живий стан»), `RELEASE_PLAN` (останній розділ). Окремо: `TECH_SPEC` §6 (ID вузлів) — відомо, що її не оновлювали.

**Б. Відповідність закритим рішенням власника.** Для кожного з `CLAUDE.md` п. 1–13: `grep` по всіх документах і коду на суперечності (термін «Залишок» — лише назви колонок БД і заборони; «Weekly Render» з грошима; нетто-агрегація грошових показників; Workload з відпрацьованим часом; «рентабельність від собівартості» на екрані портфеля; «чистий класичний EVM» без входів Archi). Кожна суперечність = знахідка DOC-RES.

**В. Довідник формул ↔ код.** Кожен ID у `docs/FORMULAS.md` має місце обчислення в SQL/вузлі й підпис на екрані; кожна формула коду має ID. Метод: зі списку ID скласти таблицю «ID → файл/вузол → цитата ≤ 3 рядки». Окремо P-02, P-09, P-10, E-02, E-05, E-08. Версія й `activeVersionId` у шапці FORMULAS = живі.

**Г. Внутрішня несуперечливість.** Одна величина — одне визначення в усіх документах (BAC, AC, EV, ETC_план/факт/прогноз, готовність ПМа, Workload, CPI «за готовністю» / «за годинами», рентабельність від контракту / від собівартості). Пара документів із різним визначенням = знахідка. Перевірити розділ «Розбіжності документів ↔ код» у `TRANSITION_PROMPT_2026-10-25.md` §11 — що з нього вже виправлено.

**Д. Застарілість і дублі.** Документи, що замінені (`archive/ARCHI_TECH_SPEC_v2_0.md`, `archive/TRANSITION_PROMPT_2026-10-15.md`, `…-25.md`, старі CTO checkpoints, `SESSION_PLAN_*`, `archive/START_PROMPT_EVM_S0.md`, `archive/archi_bot_gpt_analysis.md`): чи мають банер; чи на них ще посилаються як на еталон (grep посилань). Перелік кандидатів на архівацію — власнику.

**Е. Повнота (чого немає).** Для кожного об'єкта системи — чи є опис: таблиці й колонки (`information_schema`), в'юхи і функції (`archi_*`), тригери, вузли n8n (179) і sub-workflow (K6sm, RC7H, `nGcSyWfuMO7vjTn6`), ендпоінти вебхуків, пороги, ролі й allowlist, секрети (лише наявність), SQL-файли в `sql/` проти живої БД (чи кожен застосований; чи є живі об'єкти без SQL-файла — напр. зміни, зроблені напряму). Складіть реєстр «об'єкт → документ або ПРОГАЛИНА».

**Ж. Посилання й навігація.** Усі внутрішні посилання (`docs/…`, `§N`, `п. N`) ведуть на існуючі місця; номери розділів `RELEASE_PLAN` послідовні (є ризик дублікатів номерів «EVM-0» / «§116» від паралельних сесій); порядок читання в `CLAUDE.md` і перехідному промпті веде на актуальні файли; кожен новий документ згаданий у `README.md`.

**З. Безпека й гігієна.** Токен бота: `grep -rE "[0-9]{8,}:AA[A-Za-z0-9_-]{30,}" .` = 0; `SECURITY.md` відповідає живому стану (RLS по таблицях — SQL з `pg_class`; нова вʼю `archi_weekly_progress`; демо-дані `demo_2910` у `time_log`); немає секретів, паролів, персональних даних у `docs/` і `sql/demo_seed_*` (чи позначено їх як вигадані).

## Крок 2. Фікси (лише документи; окремий коміт на кожну групу)
Класи: **безпечні** (лічильники, версії, посилання, банери «ЗАМІНЕНО», дати) — виправляти одразу; **змістовні** (визначення, формули, рішення) — виправляти лише якщо суперечать `CLAUDE.md`, інакше — у список власнику; **структурні** (злити/архівувати/перейменувати файли) — лише за рішенням власника.
Правила з `CLAUDE.md` для оновлення документів: `FORMULAS` — разом зі зміною формули; `RELEASE_PLAN` — новий розділ у форматі «що зробив → результат → спосіб перевірки → checkpoint»; `README` — дата й версія.

## Крок 3. Звіт і завершення
Файл `docs/DOC_AUDIT_<дд.мм.рррр>.md`:
```
# Аудит документації — <дата>
Обсяг: N файлів / M рядків (з команди). Перевірено повністю: … Вибірково: … Не перевірено (чому): …
Підсумок: P0 n · P1 n · P2 n   (P0 — документ веде до неправильного рішення/цифри; P1 — суперечність між документами; P2 — гігієна)
## Інвентар  ## А…З (по розділу)  ## Реєстр «об'єкт → документ або ПРОГАЛИНА»
## Виправлено в цій сесії (коміти)  ## Рішення потрібні від власника (нумеровано, з рекомендацією)
```
Далі: розділ у `RELEASE_PLAN`, оновлення `README`/перехідного промпту, коміт, PR і merge у `main` (`CLAUDE.md` п. 6). Наприкінці — **один** блок «Рішення для власника» (до 7 пунктів, кожен: проблема → два варіанти → рекомендація).

## Критерій «аудит виконано» (усе одночасно)
1. Інвентар охоплює 100% файлів з `git ls-files` (`*.md`, `*.sql`, `*.json`, `*.py`, `*.js`) — кількість збігається з командою.
2. Розділи А–З виконані або чесно позначені «не виконано, тому що…».
3. Усі безпечні фікси зроблено й закомічено; змістовні й структурні — у списку з рекомендацією.
4. Жоден документ не суперечить `CLAUDE.md` п. 1–13 (перевірка `grep`) — або суперечність винесена власнику.
5. `README`, `TECH_SPEC`, `FORMULAS`, `TRANSITION_PROMPT` показують однаковий `activeVersionId` і кількість вузлів (з live).
6. Наступна після аудиту сесія (два режими перегляду, EVM — варіант А) має в `TRANSITION_PROMPT` оновлену вхідну точку.

## Чого не робити
Не змінювати n8n/Supabase; не видаляти файли; не вмикати RLS і не ротувати токен; не «виправляти» документи під код без рішення власника; не починати реалізацію EVM-вкладки.
