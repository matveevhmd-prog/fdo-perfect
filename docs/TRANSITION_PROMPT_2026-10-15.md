## 1. Продукт і поточна мета

**ARCHI** — оркестраційний шар над проєктними даними архітектурно-будівельного
бюро. Не ERP і не таск-менеджер: читає план (Кошторис), факт (журнали годин і
грошей), прогноз (тижневий звіт ПМа), рахує крос-перевірки й віддає власнику:

1. **Owner View** — Telegram Mini App (портфель + картка проєкту).
2. **Archi Consult** — чат-агент у Telegram (10 зафіксованих питань Q1–Q10 +
   довільні питання, формат Insight–Impact–Action).
3. **Щотижневий ритм** — звіт ПМа через бота (п'ятниця) → Weekly Render
   (таблиця на нараду) → xlsx-експорт.

Ціна (зафіксовано в TECH_SPEC): $1 000/міс (до 20 проєктів) / $500/міс (до 8).

**Поточна мета власника:** демо-відео для клієнта (`docs/DEMO_VIDEO_PLAN.md`),
на демо-даних бюро «50 виконавців». Тому зараз головне — щоб Owner View і
бот були **коректні, читабельні й узгоджені між собою** на екрані.

**Власник:** Андрій Матвєєв, COO, Telegram id `304884647` (`citydesign_ua`).
Спілкування українською. Стиль: без води, факт/припущення позначати, одне
уточнювальне питання максимум, не пропонувати обрізаних рішень, не питати
«продовжувати?» на дрібних кроках, але **питати перед кроком, що спалює >10%
ліміту сесії**. Часто надсилає скріни з рукописними позначками **без тексту** —

## 4. Архітектура даних

```
Кошторис (Google Sheets) ──(K6sm, «кошторис X» → «затвердити»)──┐
Звіт ПМа (Telegram, WR-агент) ─────────► wr_weekly_snapshots ───┤
Імпорт годин/грошей (бот) ──────────────► time_log / money_log ─┤──► тригери archi_recalc_* ──► project_metrics
Графік оплат ───────────────────────────► payment_schedule ─────┤        (SQL-функція archi_recalc(p_project))
План-колонки project_metrics ───────────────────────────────────┘
                                                                     │
                       archi_thresholds (пороги + план бюро) ───────┤
                                                                     ▼
                  n8n: Build MiniApp Data (спільний для Owner View і чату)
                       ├─► Build MiniApp HTML / Respond MiniApp Data (Owner View)
                       └─► Build Request Body → Anthropic → Sanitize Reply → Telegram (чат)
```

**Тригери (Факт, Supabase):** `archi_recalc_time` (time_log I/U/D),
`archi_recalc_money` (money_log I/U/D), `archi_recalc_wr` (wr_weekly_snapshots I/U/D),

## 6. Формули (стан на 15.10.2026, звірено з кодом/SQL)

> **Канон — `docs/FORMULAS.md`** (ID F-/S-/P-/V-/R-). Нижче — короткий конспект
> для орієнтації; при розбіжності правий FORMULAS.md.

### 6.1 `archi_recalc()` (SQL, Supabase) — на рівні проєкту
- `actual_hours` = Σ `time_log.години` (статус `confirmed`).
- Вартість команди = Σ годин × `rates.razom_grn_god` (за посадою виконавця)
  або `real_rate_team_hour` проєкту, якщо посади немає в `rates`.
- `actual_cost` = вартість команди + оплати субпідрядникам (`money_log`
  тип `оплата_субпідряднику`).
- `acts_amount` / `money_received` = Σ `money_log` тип `акт_підписаний` /
  `надходження_від_замовника`.
- `hours_remaining` = `planned_hours − actual_hours` (у чаті це **ETC_факт**, у
  картці Mini App показується як **ETC_Total «План»** — див. 9.3).
- По стадіях МБР/ЕП/П/Р: план = `etc_plan_by_stage[s]` (**повний план годин
  стадії**, не залишок); ETC_прогноз = зі знімка ПМа; якщо готовність ≥100 або
  план стадії = 0 → 0; інакше NULL.
- `etc_forecast_total_hours` = Σ ETC 4 стадій **лише якщо всі 4 є**, інакше NULL.
- `pct_complete` = Σ(готовність_s × план_s) / Σ план_s (лише коли є всі 4).
- `cost_final_forecast` = actual_cost + ETC_Total × `real_rate_team_hour` +
  max(план субпідряду − сплачено, 0).
- `profit_forecast` = контракт − cost_final; `profitability_forecast_pct` =
  profit_forecast / контракт × 100 (**база проєкту — контракт**).
- `forecast_confirmed_pct/week` — останній ненульовий прогноз (показується, коли
  поточний NULL).
- `earned_value_contract` = контракт × pct_complete; `ev_classic_evm` = bac ×
  pct_complete; `cpi_classic_evm` = ev_classic / actual_cost.
- `nearest_act_*` — перший акт у `payment_schedule` без підписаного акту стадії;
  `nearest_doc_deadline` — перша документація стадії з готовністю <100;
  `doc_issuance_probability` = зі знімка ПМа, інакше з графіка.

### 6.2 Сигнали й кольори проєкту (`Build MiniApp Data`)
Пороги — з `archi_thresholds` через `rule(key, default)`:
- **Рентабельність:** немає прогнозу → 🔴; прогноз <0 або нижче плану на
  ≥`rent_drop_pp_red` (10 п.п.) → 🔴; ≥`rent_drop_pp` (5) → 🟡.
- **Прибуток:** немає прогнозу / <0 / нижче плану на ≥`profit_red_pct` (10%) → 🔴;
  ≥`profit_yellow_pct` (5%) → 🟡.
- **ETC:** прогноз більший за `hours_remaining` на >`etc_red` (10%) → 🔴,
  >`etc_yellow` (5%) → 🟡; оптимістичний прогноз (6.4) → 🟡.
- **Не оплачено** (виконано − оплачено) > `unpaid_red` (25% контракту) → 🔴,
  > `unpaid_yellow` (10%) → 🟡. Виконано − акти > 10% контракту → 🟡 «акти».
- **CPI** < 0,85 → 🔴, < 0,95 → 🟡.
- **Терміни** стадії: зсув > `slip_red_days` (14) → 🔴, > 0 → 🟡.
- **Документація:** ймовірність ≤3 → 🔴, ≤6 → 🟡.
- **⛔ Блокер:** днів простою ≥ `block_red_days` (14) → 🔴.
- **⚖️ Розбіжність готовності** (`readiness_gap_pp` 20) — пише ПМ при підтвердженні.
- Статус проєкту = 🔴, якщо є хоч один червоний сигнал; 🟡 — жовтий; інакше 🟢.

## 9. Знахідки (дефекти й ризики; статус — реєстр у розділі «Карта»)

### 9.1 `WR: Schedule Reminder (Fri 10:00)` — мертвий вузол (**Факт**)
Немає вихідних з'єднань; параметри в UI-експорті — лише `mode: everyWeek`

Рішення власника (§ відкриті з попередніх сесій): потрібне нагадування чи ні.

### 9.2 Чат, імовірно, бачить 0 КП і Прогноз проєктів = Факт — **ВИПРАВЛЕНО 15.10.2026 (RELEASE_PLAN §48)**
> Тепер `Fetch KP Log Sum (Chat|MiniApp)` → `Fetch Project Metrics (…)` послідовно; порядок гілок
> більше не впливає. Живим чатом ще не перевірено (свіжих chat-executions не було).

`Is Owner View Request?` (false) → дві сестри: `Fetch Project Metrics (Chat)`
(позиція y=0) і `Fetch KP Log Sum (Chat)` (y=608). При `executionOrder: v1`
n8n виконує гілки за позицією зверху вниз, тож весь ланцюг
`Build MiniApp Data → … → Send Reply` проходить **до** вузла КП;
`try/catch` повертає 0. У Mini App вузли на одній висоті (y=400), КП лівіше
(x=−208) і виконується першим — тому Owner View показує 5 КП коректно.
Перевірка: execution чату (`search_workflow_executions` → `get_workflow_execution`),
подивитись `pfc.kpMonthSent` у виході `Build MiniApp Data`.

### 9.3 Методологія ETC у картці (**Факт про код; оцінка — Потребує рішення власника**)
1. Стадійний блок «ETC, год»: «План» = **повний план стадії** (`etc_plan_by_stage`),
   «Прогноз» = залишок ПМа, «Різниця» = прогноз − повний план. Залишок не
   порівнюється з плановим залишком. Приклад DEMO-03 П: план 337, факт 194,2,
   прогноз 150 → «Різниця −187», хоча відносно планового залишку (142,8) прогноз
   на +7,2 год **гірший** за план.
2. Той самий підхід у сигналі «оптимістичний прогноз» (6.4).
3. ETC_Total «План» у картці = `hours_remaining` (планові години **з АН** мінус
   факт), «Прогноз» = Σ 4 стадій **без АН** (`planned_hours_by_stage` має
   стадію «АН», 75–88 год у DEMO, вона не входить у ETC). Прогноз систематично
   менший на години АН.
4. Глосарій чату: «ETC_факт = ETC_план − Фактичний_час» = `hours_remaining`;
   у картці те саме значення підписано «План». Одна величина — дві назви.
Це питання до власника + розділ `FORMULAS.md`, не тихий фікс.

### 9.4 Чат не знає про план бюро — **ВИПРАВЛЕНО 15.10.2026 (RELEASE_PLAN §48)**, Q6/Q7 цитують `pfc`
Q7 («Чи виконуємо річний план по прибутку?») у `Build Request Body` інструктує
LLM: «річного плану компанії в даних немає». План є (`plan_year_*`, рядки
таблиці портфеля). Q6 («на який час у команди є робота») теж не використовує
84 000 год і Workload. Чат і Owner View зараз розходяться в цих відповідях.

### 9.5 Кнопка меню «📄 Договір» іде в чат-LLM (**[Припущення]** за кодом, перевірити наживо)
`WR: Hard Logic Engine` має `PICK['договір']`, але `WR: Determine Route` не
включає «договір» у `isWrCommand` → повідомлення йде гілкою чату (LLM-відповідь),
а не на вибір проєкту. Навіть якщо дійти до вибору, кнопка «📄 договір 24-11»
не пройде regex `^договір\s+…$` (емодзі на початку).

### 9.6 Подвійні відповіді (**[Припущення]**, перевірити)
«КП: 5» і «договір X» обробляються своїми гілками **і** паралельно головною
гілкою, яка, не впізнавши WR-команду, доходить до чату → LLM теж відповідає.

### 9.7 Безпека й гігієна (відомі, рішення власника)
Токен бота в коді (3 вузли, включно з URL `M: Send Project Picker`); чат без
allowlist; RLS вимкнений; `WR: Ensure Mode Table`/`Ensure Plan Table` виконують
DDL на кожне повідомлення; SQL у `Import/Meeting: Insert …` збирається
рядком (частина полів екранована, §20); `Read Mode` підставляє chat.id у SQL
(числове, ризик низький).

### 9.8 Демо-дані (для відео)
Факт-рентабельність портфеля −65,5% і прибуток факт −2,4 млн — наслідок
формули «акти − собівартість» при малих актах (DEMO). Власник бачив; для

## 11. Як технічно працювати (уроки цієї сесії)

**n8n MCP:**
- `update_workflow` має лише `setNodeParameter` (повна заміна значення:
  `/jsCode`, `/query`, `/text`); patch-операції немає. Тому кожна правка
  Code-вузла = повний текст вузла (Build MiniApp Data ~28 КБ, HTML ~26 КБ).
- Зберігати робочі копії вузлів у scratchpad, правити Python-скриптом
  (`assert old in s; s.replace(old, new, 1)`), `node --check`, потім передавати
  повний текст. Scratchpad між сесіями **не зберігається** — актуальний код брати
  з живого n8n (`get_workflow_details` → файл → Python) або з
  `workflows/DEMO_Archi_Agent_Core.json`.
- `Build MiniApp HTML` — HTML у JS template literal: не вживати `` ` `` і `${`;
  частина рядків у ньому вже записана як `\uXXXX` (подвійне екранування
  `\\u…` у JSON-параметрі = літерал `\u…` у коді — це нормально).
- Після `publish_workflow` — `get_workflow_details` (результат ~270 КБ іде у
  файл), порівняння live == local **після декодування `\uXXXX`** (n8n частину
  escape-послідовностей зберігає розкодованими). Розбіжність лише в коментарях —
  прийнятна, але назвати в RELEASE_PLAN.
- `versionName` ≤ 80 символів.
- Експорт у репо: `json.dumps(workflow, ensure_ascii=False, indent=2)` +
  заміна `(?<=bot)\d{8,}:[A-Za-z0-9_-]+` → `<TELEGRAM_BOT_TOKEN>`; перевірити,
  що в файлі немає `\d{8,}:AA…`.
- `test_workflow` виконує неспіновані credential-вузли по-справжньому
  (урок §10) — пінувати всі downstream Postgres/HTTP вузли.

**Supabase MCP:**
- Багатооператорний SQL інколи «cancelled» — один оператор або `DO $$ … $$`.
- `archi_thresholds.value` — numeric (без лапок).
- Зміни `archi_recalc()`: `pg_get_functiondef` + `replace` + `EXECUTE` у `DO`,
  тест — з `RAISE EXCEPTION` для відкату.
- Видалення через MCP може бути заблоковане — не обходити, просити власника.

**Репозиторій (CLAUDE.md п.6):** лише `matveevhmd-prog/fdo-perfect`; робоча гілка від `main`;
кожна зміна в n8n/Supabase → той самий коміт: експорт JSON, README (versionId), новий розділ
RELEASE_PLAN (зроблено → результат → перевірка → checkpoint), за потреби
TECH_SPEC/FORMULAS/SECURITY. Коміт-повідомлення українською. **Кінець сесії — PR і злиття в
`main`** (рішення власника 15.10.2026), щоб наступна сесія стартувала з актуальних документів.

**Перевірка «готово»:** SQL/execution/скрін власника, не «status: success».
Не писати «зроблено» про те, що не бачив на екрані, — писати «не перевірено
наживо».
