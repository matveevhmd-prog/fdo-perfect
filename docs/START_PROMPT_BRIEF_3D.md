## 2. Рішення, які вже прийнято (не перепитувати)
- Шапка з датами звітів.
- «Стан портфеля» — брутто (п. 11): прогноз нижче плану і вище плану окремо; проєкт без прогнозу (24-37) — окремим рядком.
- «Рентабельність ціни» (P-07) і «Рентабельність витрат» (P-04), з поясненням дрібно під кожною; порівняння з двома базами: річна ціль бюро з довідника і сума планів проєктів — окремими рядками.
- Незданий звіт за минулий закритий тиждень → доручення ПМу (правило `no_report` в SQL), не сигнал «прогноз застарів» (п. 26).
- Групування за проєктом: усе про проєкт — в одній дії; у дії «Акти» лише проєкти без власної дії.
- Акти — усі прострочені за графіком договору, без порогу (п. 15).
- Акт лише за складом стадії в договорі; «проміжний акт» не пропонувати (п. 45).
- Пари площин, чотири ситуації (стоїть / горить / готовність падає / росте без годин), переробка після 100% (п. 45).
- Переробка ловиться через ETC_прогноз і ланцюжок п. 7 (E-03 «Готовність за прогнозом», «Ефективність годин» = план ÷ (факт + прогноз)); вікно — п. 37. Формулу P-10 не міняти (Н-1 знято).
- Адресат дії — з правила SQL/RACI; без правила — «пропозиція» (п. 32). У `archi_morning_brief` уже є правила: blocker (замовник → власник, дзвінок; гроші → Фіндиректор; люди → ПМ, ГАП, Головний конструктор), act_due, etc_red, rent_below, no_forecast, no_report, pm_escalation, client_unpaid, sub_blocked, doc_deadline, meeting_due.
