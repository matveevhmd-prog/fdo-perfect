## Роль і режим
Ти виконуєш рішення власника за підсумками аудиту, а потім починаєш наступну місію. Змінювати n8n і Supabase **можна лише** там, де власник прямо дозволив (кожна така зміна — за правилами `CLAUDE.md` «Правила n8n через MCP» і тригерами стопу). Документи без рішення власника не видаляти.

## Крок 0. Старт (15 хвилин)
1. `CLAUDE.md` повністю (п. 1–14).
2. `docs/DOC_AUDIT_<дата>.md` — **повністю**; окремо: «Рішення для власника» і колонку «Виправлено в цій сесії».
3. Найновіший `docs/TRANSITION_PROMPT_*.md` і `docs/RELEASE_PLAN.md` з кінця (розділ про аудит).
4. Звірити живий `activeVersionId` n8n з `README.md` і `workflows/DEMO_Archi_Agent_Core.json`; звірити кількість вузлів. Розбіжність → довіряти n8n.
5. Прогнати: `python3 scripts/check_report_form.py`; `node tests/wr_parse_agent_output/run.js`.

## Крок 1. Рішення власника → виконання
Власник відповідає на пункти блоку «Рішення для власника» у чаті або у файлі аудиту. Для кожного пункту:
- Записати рішення в `CLAUDE.md` (якщо це закрите рішення) — **тієї ж хвилини**, до коду.
- Виконати; змінюючи формулу, поріг чи підпис — оновити `docs/FORMULAS.md` **тим самим комітом**.
- Структурні рішення (архівація/злиття/перейменування файлів) — з оновленням усіх посилань; перевірка: `grep` старої назви = 0.
- Пункт без відповіді власника **не виконувати** і не вирішувати за нього; повторно нагадати одним рядком у кінці сесії.

## Крок 2. Закрити знахідки аудиту
Порядок: P0 → P1 → P2. Для кожної знахідки — статус у таблиці `DOC_AUDIT`: «виправлено (коміт) / відкрито (чому) / чекає рішення власника». Знахідки типу «код ≠ документ» — спершу питати власника, що правильно (код чи документ).
Відомі перенесені знахідки (перевірити їхній статус в аудиті): CTO #1 `AN: Attach Block` дублює пороги; CTO #2 токен у публічній історії git (рішення власника про ротацію); CTO #3 демо-години `demo_2910` у `time_log` (відкат перед Ф3); індекс P-10 у Weekly Render не реалізовано (`CLAUDE.md` п. 12).

## Крок 3. Повторний аудит-контроль
Після виправлень — скорочений перепрогін перевірок А (правдивість проти живого стану), Б (суперечності з рішеннями власника) і Ж (посилання): результат у `DOC_AUDIT` розділом «Контроль». Критерій: P0 = 0; кількість відкритих P1 = 0 або кожна має рішення власника.

## Крок 4. Наступна місія — «два режими перегляду» (лише після кроків 1–3)
Мета: власник перемикає режим і бачить ті самі проєкти двома оптиками — **ARCHI** (вже є) і **EVM (класичний)** (будувати). Вимоги власника (`CLAUDE.md` п. 8, 13):
- Класичний EVM — **в чистому вигляді, без входів Archi**: жодної готовності ПМа (E-02), «Ефективності виконання», P-10, порогів і кольорів Archi.
- **Варіант А (рішення 29.10.2026):** EV = Σ по пакетах робіт (бюджет пакета × правило виконання, напр. 0/100 по виданих аркушах/розділах); PV — обов'язковий (розклад пакетів у часі); потрібна розбивка робіт на пакети в Кошторисі.
- Початок — **Ф0** з `docs/EVM_CLASSIC_PLAN.md`, але **план переглянути** (він має EV = BAC × готовність ПМа і опційний PV — це суперечить вимозі). Результат Ф0: `docs/EVM_CLASSIC_DESIGN.md` — пакети робіт, правила виконання по стадіях (МБР, ЕП, П, Р), формули K-01…K-12, структура Кошторису; перший крок — прочитати реальну вкладку Кошторису (Google Sheets MCP; Факт: K6sm читає лише `A1:X27` і `Графік_оплат`).
- **Питання власнику до коду (одне, якщо ще не закрите):** правило виконання пакета для кожної стадії (напр. «аркуш виданий замовнику = 100%»).
- Не змішувати: нові назви, нова база, окремі SQL-в'ю; інваріант єдиного обчислення (`TECH_SPEC` §2.1) — рахує SQL, JS лише показує; нова таблиця — з RLS (Р11) і записом у `SECURITY.md`.
- Перед **будь-якою** пропозицією — блок «місце, вплив, борг, масштаб» (`CLAUDE.md`). Спершу архітектура від кінця до початку.

## Критерій «виконано» (усе одночасно)
1. Кожен пункт блоку «Рішення для власника» має статус: виконано / чекає відповіді.
2. P0 = 0; відкритих P1 без рішення власника немає.
3. `README`, `TECH_SPEC`, `FORMULAS`, `TRANSITION_PROMPT` показують однаковий `activeVersionId` і кількість вузлів (з live).
4. `docs/EVM_CLASSIC_DESIGN.md` створено (Ф0) або чесно записано, чому ні; жодного рядка коду EVM-вкладки без погодженого дизайну.
5. Усе злито в `main`.
