### П2b — дизайн картки чату (15.11.2026, до коду; Q1 і загальні питання, шаблон GENERIC_CARD)
**Корінь B-01 (Факт: код + live SQL 15.11):** `Build Request Body` передає LLM колір лише `cls.received`; `cls.etc/profit/rent/cpi` лишаються в `Build MiniApp Data` (live: `DEMO-05 cls.etc = red`, `etc_gap_signal = red`), LLM розфарбовує сам.
**Межа (не вигадувати):** змінюються лише Q1 і загальні питання (картка проєкту). Q2…Q10 не чіпати, крім B-15 (прибрати слово «код» з заголовків фокусу Q3/Q4/Q5). Mini App (B-19 у Owner View, B-03 у картках АН) — окремий вузол `Build MiniApp HTML`, не входить.
**Розподіл:**
1. `Build Request Body` (код): вибір до 3 проєктів (⛔, 🔴, 🟡; всередині — найнижча рентабельність прогноз; якщо питання називає ID — вони), збір деталей картки і вихід `cardData`.
2. LLM: лише JSON `{"cards":{"<ID>":{"insight":"","impact":"","action":""}}}`. Колір, числа, заголовки не пише.
3. `Sanitize Reply` (код): парсить JSON, перевіряє числа (кожне число в тексті LLM має бути в фактах проєкту: сигнали, проблеми, прохання ПМа, показники), складає картку, валідатор B-17 лишається.
**Поля картки (один показник — один рядок, п. 4):** заголовок `⛔/🔴/🟡/🟢 <b>ID</b>`; «Години»: ETC_план, Фактичний_час, ETC_факт, ETC_прогноз, Різниця ETC + `cls.etc`; «Гроші»: Прибуток_план, Прибуток_прогноз + `cls.profit`, Рентабельність_план, Рентабельність_прогноз + `cls.rent`, Не оплачено + `cls.received` (лише > 0), Ефективність (гроші, ПМ) + `cls.cpi`; «Проблеми»: блокер (⛔, дні, тип), потім текст ПМа, інакше «немає»; далі Insight / Impact / Action. Негативне число — 🔴 перед ним (п. 15). Єдиний форматер: кома, `п.п.`, `г`.
**Запасний шаблон (без LLM):** при невалідному JSON, відсутньому проєкті в JSON або числі, якого немає у фактах: Insight = перший 🔴/🟡 сигнал SQL, Impact пропускається, Action = «Прохання ПМа» або «уточнити в ПМа».
**Заголовок і підсумок:** «Станом на ДД.ММ.РРРР», портфель (лічильники з `summary` коду), решта проєктів — один рядок з ID і кольором (код, не LLM).
**B-16 (критерій Q3):** не робиться тут. Q3 відбирає проєкти з проханням ПМа, блокером чи без прогнозу — це поточне правило коду, а не помилка; зміна критерію (чи брати 🔴 без прохання) — рішення власника.

### П2e — дизайн аналітики картки і портфеля (16.11.2026, до коду)

**Причина (власник, 16.11.2026):** методологія ARCHI — ШІ-аналітик над даними: аналізує стан проєктів і пайплайну, дає власнику коментарі й поради. Поточна картка (П2b–П2d) — це показ даних із підписами: Insight переказує сигнали, Impact повторює один показник, блоку рівня портфеля немає. Варіант «Impact кодом» (П2e v1) знято як такий, що зменшує аналітику (п. 19, п. 32).
**Принцип:** код і SQL рахують факти й наслідки в числах; LLM-аналітик пояснює зв'язки, розставляє пріоритети, радить дію; числа в його тексті перевіряє код (правило п. 9: лише з даних).

**Факти для LLM (джерело — SQL, п. 31; функція `archi_card_facts(company)`, міграція — лише за «так» власника):**
| ID | Факт | Формула | Рівень |
|---|---|---|---|
| F1 | Відхилення прибутку | `profit_forecast − profit_plan`, грн | проєкт |
| F2 | Вартість простою | контракт блокованого проєкту, дні простою, причина, «Потрібно» | проєкт |
| F3 | Частка в портфельному відхиленні | F1 проєкту ÷ Σ від'ємних F1, % | проєкт |
| P1 | Портфель: прогноз прибутку проти плану | `pfc.forecastProfit`, `pfc.planProfit` | портфель |
| P2 | Концентрація втрат | перші 3 проєкти за F1 і їх частка в Σ від'ємних F1 | портфель |
| P3 | Заблоковано | Σ контрактів з блокером, кількість, причини (люди / гроші / замовник) | портфель |
| P4 | Прохання ПМів | список «ID — прохання» | портфель |
| P5 | Касовий ризик | Σ «виконано і не оплачено», `unpaidHours` | портфель |
| P6 | Пайплайн продажів | КП надіслано за рік / план року, за місяць, прогноз договорів (`pfc.kp*`) | портфель |
Існуючі сигнали проєкту (колір, терміни, ETC, ймовірність акту/документації) лишаються джерелом правди без змін.

**Правдивість (замінює фільтр слів з П2d):** висновок допустимий, якщо спирається на названі факти; причинні зв'язки — лише між наведеними фактами; Impact проєкту має містити щонайменше одне число з фактів цього проєкту; число поза набором фактів → текст відкидається кодом (механізм `cardNums` з П2b розширюється на F/P). Слова-ознаки («ризик», «буде») не забороняються: прогноз із числом із даних — це аналіз, без числа — вигадка.

**Вихід LLM (JSON):** `{"portfolio":{"headline":"…","priorities":["…","…"],"pipeline":"…"},"cards":{"<ID>":{"insight":"…","impact":"…","action":"…"}}}`.
**Показ:** блок «🧭 Висновок Archi» одразу після лічильників портфеля: рядок-висновок, 2–3 пріоритети («Спершу: …»), рядок про пайплайн. Ліміт блоку 900 символів; поточне повідомлення Q1 = 2 494 з 4 096 (Факт: офлайн на live SQL), запас є. Немає `portfolio` у JSON → блок не показується, нічого не підставляється.
**Не входить:** Owner View, Weekly Render, Q2–Q10 (вони вже вільний текст LLM зі своїми промптами), ліміт «3 картки» (лишається параметром коду; питання відкрите).

**Критерії результату:** (1) JSON парситься; (2) 100% чисел у тексті ∈ фактів (код + ручна звірка всіх рядків на live SQL); (3) Impact кожної картки має число; (4) блок портфеля називає щонайменше 2 проєкти й пайплайн; (5) повідомлення ≤ 3 900 символів; (6) час і токени з виконання n8n; (7) скрін власника.

**Модель і промпт — узгодити з власником ДО публікації:** варіанти (А) лишити `claude-sonnet-4-6` (виміряно: 8,5–8,8 с, 414–437 токенів на 3 картки); (Б) `claude-sonnet-5-5`; (В) `claude-opus-5-5`; (Г) `claude-haiku-5-5`. Швидкість і ціна Б, В, Г — не виміряні; вимір — одне виконання кожної моделі на тому самому промпті (заміна рядка `model` у `Build Request Body`). Бюджет власника — $80 на клієнта на місяць (п. 33), ціна запитів — за прайсом Anthropic, не перевірено. Чернетка промпту — `scripts/chat_card/prompt_p2e_draft.md`.
