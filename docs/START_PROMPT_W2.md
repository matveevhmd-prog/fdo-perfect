## Модель (власник, 22.11.2026; п. 41)
• **Кошторис — файл** (Google-таблиця або Excel) у сховищі компанії. Створюється на етапі комерційної пропозиції (ціна й обґрунтування) або після договору. Після підписання він — **додаток до договору** разом з ТЗ і вихідними даними; його дедлайни — дедлайни договору, його графік актів — акти договору. Далі це база проєкту; **зміни лише через Додаткову угоду**.
• Файл завантажується в ARCHI **через Telegram-бота** (або збирається через API Google Диска). Завантаження запускає створення проєкту. З ARCHI до першоджерела веде **посилання на файл**; Кошторис у ARCHI не рендериться.
• **Формули плану лишаються у файлі** (власник прописував їх пів року; не переписувати). Supabase: зберігає версію (рядки й підсумки), перевіряє, що підсумки файлу = перерахунок із рядків (контрольні перевірки, як K1–K11 у K6sm), рахує все від факту й прогнозу (`archi_recalc`).
• **Санкція змін:** будь-яку зміну планових цін санкціонує лише власник коментарем (також через ARCHI: «санкціоную рентабельність 20%»); коментар розглядається на щотижневій нараді або окремо; правки у файлі вносить ПМ. Захист з файлу знімає власник (підтверджено 22.11.2026).
• **Документи проєкту** копіюються в ARCHI з посиланнями: КП, договір, додаткові угоди, підписані акти, ТЗ, вихідні дані (Диск або «Вчасно»). Вкладка «Кошторис» веде до них, щоб власник міг переконатися, що ціна в контракті саме така.

## Закриті рішення (не перепитувати)
• Назви: «Кошторис», «версія Кошториса», «зміна ТЗ»; таблиці `koshtorys_*`.
• GATE: автоматизований статус «затверджено власником»; бот лише попереджає про списання годин без затвердженої версії.
• Імпорт файлу через бота — основний шлях; **редагування рядків у Mini App не потрібне**.
• Графік оплат входить у версію Кошториса.
• 4 реальні проєкти (`22-24`, `24-11`, `24-37`, `24-52`): файлів немає — рядки генеруються за підсумками, `source='demo_derived'` (правило сесії 9, п. 18).
• Причини змін: «зміна вимог замовника», «вихідні дані надано не повністю», «помилка виконавця», «зміна обсягу за ініціативою бюро», «інше». Зміну завжди затверджує власник.
• Нагляд (`<id>-АН`) ведеться в Кошторисі з версіями: виїзди, ціна виїзду, години на виїзд, ставка; контракт, години, рентабельність рахує SQL (F-27).
• Пакети класичного EVM: бюджет = сума рядків затвердженого Кошториса по розділу й стадії; дати, розподіл бюджету ролей, правило «видано» — окремо в `evm_packages` (гілки не змішувати, п. 14).
• Назви змін: на екрані «Оплачує замовник», «За гроші власника», «Ще не звірено»; у базі `customer`, `owner_funded`, `undetermined`; поле «Хто платить за зміну» (не плутати з п. 11).
• Сутність «Додаткова угода»: статуси «готується / надіслано на підпис / підписана / відхилена», номер, дата, що змінилось, файл. **Хто платить за зміну виводиться з неї**: підписана → «Оплачує замовник»; не підписана, роботи виконуються → «За гроші власника»; ще не звірено → «Ще не звірено».
• П. 39: виконавці бачать усе, крім грошей; маскування — у SQL за роллю. Співвласник = роль `owner`; ГАП до окремого рішення як виконавець.
• Вкладка «Кошторис» — **усередині Owner View** (шоста після «Рентабельність», «Прибуток», «Акти і гроші», «Години», «Ефективність»; `TAB_DEFS` у `Build MiniApp HTML`).
